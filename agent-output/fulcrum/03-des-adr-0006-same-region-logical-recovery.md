# ADR-0006: Same-region logical recovery within the LRS constraint

> Generated by design agent | 2026-11-09
>
> Status: Recorded approved design decision; implementation Unverified  
> Date: 2026-11-09  
> Deciders: Project Stakeholders through the actual DEV Gate 2 approval

## Context

[Architecture — Reliability assessment](02-architecture-assessment.md#-reliability-assessment-510):
> Logical RTO4h/RPO1h are untested; Cosmos asynchronous backup behavior is not an achieved RPO.

[Requirements — Backup and recovery](01-requirements.md#backup-and-recovery)
set planning objectives, not a regional-loss guarantee.
[Manifest `storage-blob-replication`](contracts/sku-manifest.json) retains the
original user LRS pin; Standard GPv2/non-HNS/Hot is the PITR-eligible account shape.

## Decision

Record paid Cosmos continuous 30-day backup and one monthly 10GB source restore
to a **new Sweden Central account**, with temporary account/PE access for 4h,
1 million RU and 10GB live/paid-backup conservative storage allocations.
Reapply private DNS/grants and cut over the application endpoint.

Keep Blob PITR 30 days, versioning, soft delete/change feed at least 31 days,
container soft delete and account deletion lock. Approved scenario: 20GB live,
10GB aggregate protected versions/deletions, 0.5GB feed; one 20GB logical restore
with 0.5GB processed feed. Lifecycle must preserve recoverable versions.
Source-owned image/configuration recreation covers compute; do not add a vault.

## Alternatives Considered

| Alternative | Benefit | Rejection / trade-off |
| --- | --- | --- |
| Geo-replicated Blob / second workload region | Broader geographic recovery options | Conflicts with explicit LRS/single-workload-region constraint; not approved or priced. |
| Treat PITR as whole-account or regional disaster recovery | Simpler recovery story | Unsupported by the approved scope: account protection and same-region logical recovery are not regional-loss guarantees. |

Sources: architecture Reliability assessment and
[complete dependency closure](_meta/02-final-dependency-closure.md).

## Consequences

- **Positive:** addresses scoped corruption/deletion/application faults with
  explicit paid restoration and endpoint/identity reconstruction.
- **Negative:** LRS, one worker and single region retain outage exposure; Blob
  PITR does not restore an entirely deleted storage account.
- **Neutral:** the temporary Cosmos PE is conditional, not a fifth steady
  production dependency. Source restore is billed once, not again on the target.

## WAF Pillar Analysis

| Pillar | Approved trade-off |
| --- | --- |
| Security | Restore requires private access and reapplication of data grants; recovery credentials are not embedded. |
| Reliability | Recoverable logical faults addressed; 4h/1h objectives and cutover remain untested. |
| Performance | Restore progress and application validation must fit the objective; no measured restore speed. |
| Cost | Paid 30-day backup, restore feed and temporary target/PE explicitly allocated; no free backup assumption. |
| Operations | Operators need full access/DNS/RBAC/rebind/validation runbooks, not just a restore command. |

## Compliance Considerations

**Assumed Corp policies—not tenant-verified; DEV Architecture-only.**
Backups and restore targets remain Sweden Central. Accepted ACR artifact pairing
does not extend to Cosmos/Blob recovery or authorize optional geo-replication.

## Implementation Notes

Recovery/application owners later drill corruption/deletion, point selection,
TTL/index correctness, grant/DNS reapplication, endpoint cutover and user-visible
validation. No actual restore, account creation or resource deletion is authorized.

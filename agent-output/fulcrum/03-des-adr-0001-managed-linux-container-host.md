# ADR-0001: One managed Linux B1 container host

> Generated by design agent | 2026-11-09
>
> Status: Recorded approved design decision; implementation Unverified  
> Date: 2026-11-09  
> Deciders: Project Stakeholders through the actual DEV Gate 2 approval

## Context

[Architecture — Executive Summary](02-architecture-assessment.md#-executive-summary):
> Use a small managed modular-monolith-compatible platform: one Linux App Service B1,

[Requirements FR-01 / FR-08](01-requirements.md#core-infrastructure-capabilities)
require a Linux container platform and repeatable infrastructure, not application
implementation. [Performance assessment](02-architecture-assessment.md#-performance-assessment-610)
records the memory envelope; CPU, concentrated concurrency and latency are untested.

## Decision

Record one Linux App Service B1 worker, 730 hours/month, as already selected in
[manifest rev 2, `app-host`](contracts/sku-manifest.json). Use private inbound
App/SCM access and separate outbound VNet integration; retain Always On and the
approved private ACR managed-identity image-pull route. No slots, autoscale,
zonal redundancy or filesystem-backup capability is asserted.

## Alternatives Considered

These are the existing source-screened alternatives, not a new evaluation.

| Alternative | Benefit | Rejection / trade-off |
| --- | --- | --- |
| B2 | More worker capacity | The approved memory envelope fits B1; higher ongoing cost without measured need. Reconsider only through the architecture owner after load evidence. |
| Free / Shared hosting | Lower nominal host charge | Excluded by the approved private-host capability screening; does not satisfy this design. |

Source: [SKU recommendations and alternatives](02-architecture-assessment.md#-resource-sku-recommendations)
and [existing SKU comparison](03-des-sku-comparison.md).

## Consequences

- **Positive:** small managed hosting footprint, no additional orchestration platform.
- **Negative:** one worker and non-zonal deployment accept DEV downtime; sizing fit
  does not establish API latency or peak capacity.
- **Neutral:** application team supplies the image, runtime, configuration/health
  interface and every application test; Bicep implementation remains later.

## WAF Pillar Analysis

| Pillar | Approved trade-off |
| --- | --- |
| Security | Private ingress and MI pull; actual grants, image routing and DNS need tests. |
| Reliability | Simplicity instead of workload HA; no numeric end-to-end availability guarantee. |
| Performance | Memory-screened B1; CPU, cold start, 10–100 concurrent users and typical API under 2s remain unverified. |
| Cost | Smaller compared worker; paid 730h allocation, no free-tier assumption. |
| Operations | Managed platform reduces host administration; image/startup diagnostics remain essential. |
